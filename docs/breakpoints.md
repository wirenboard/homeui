# Брейкпоинты и размеры для проверки

Вёрстка переключается на трёх ширинах окна. Значения заданы в `frontend/src/common/breakpoints.ts`
(TS) и `frontend/src/common/breakpoints.css` (CSS, `@custom-media`). Числа в `@media` и
`useMediaQuery` в коде компонентов не пишутся.

## Режимы

| Режим | Ширина окна | Эталон | Что меняется при входе |
|---|---|---|---|
| телефон | 360–767 | Samsung Galaxy A, 360×800 | бургер, одна колонка, консоль снизу, мобильные варианты страниц |
| планшет и ноутбук без меню | 768–1023 | iPad вертикально, 768×1024 | десктопная вёрстка контента, меню остаётся бургером |
| планшет и ноутбук с меню | 1024–1365 | iPad горизонтально, 1024×768 | боковое меню вместо бургера |
| десктоп | от 1366 | ноутбук 1366×768, монитор FHD | консоль справа, панели рядом с контентом |

## Проверка перед PR

Изменения UI смотреть на нижнем и верхнем крае каждого режима, который они задевают. Высота
везде 600:

360×600, 767×600, 768×600, 1023×600, 1024×600, 1365×600, 1366×600, 1920×600.

Проверка делается перед открытием PR и на ревью PR, если изменены `frontend/src/**/*.css` или
`*.tsx`. После каждой правки её гонять не нужно.

### Как проверять

1. **Найти страницы.** Взять изменённые файлы ветки относительно `origin/master` и найти страницы, к
   которым они относятся, по `frontend/src/router/routes.tsx`. Файл из `src/pages/<x>/` относится к
   своей странице. Для общего кода (`src/components`, `src/layouts`, `src/common`) найти страницы,
   которые его импортируют. Правка меню или общей раскладки задевает все страницы, тогда хватит
   нескольких: дашборд, `/devices`, `/settings/logs`. Если изменение видно только в состоянии, до
   которого не дойти по адресу (выбранное DALI-устройство, открытая модалка, результат скана), или
   непонятно, какие страницы смотреть, агент спрашивает у человека.
2. **Запустить dev-сервер** против стенда: `cd frontend && npm run dev`. Адрес контроллера берётся из
   `MQTT_BROKER_URI`. Логин и пароль стенда агент спрашивает у человека, в код и документы они не
   пишутся.
3. **Снять страницы:**
   ```sh
   cd frontend
   SCREENS_LOGIN=<логин> SCREENS_PASSWORD=<пароль> npm run screens -- /settings/dali /settings/logs
   ```
   Снимки сохраняются в `frontend/.tmp/screens/<страница>-<ширина>x600.png`. Каталог задаёт
   `SCREENS_OUT`.
4. **Просмотреть снимки.** Что ищем:
   - горизонтальную прокрутку, обрезанный справа контент, наложение элементов;
   - сжатые или пропавшие панели на страницах во всю высоту (DALI, консоль);
   - смешанную вёрстку на краях режимов: на 767 и 768 разная вёрстка контента, на 1023 и 1024 бургер
     и боковое меню, на 1365 и 1366 консоль и боковые панели;
   - текст и кнопки, которые не помещаются на 360.
5. **Отчитаться** таблицей «страница × размер» с найденными проблемами и путями к снимкам. Агент
   ничего не исправляет без согласия человека.

## Почему так

- **360 минимум.** Самая узкая массовая ширина телефонов. Уже 360 вёрстка не гарантируется.
- **Размер окна, а не экрана.** Из экрана вычитаются панели ОС и браузера.
- **Высота 600.** Брейкпоинтов по высоте нет. Страницы во всю высоту окна (DALI, консоль) должны
  работать от 600. Это окно браузера на ноутбуке 1366×768 с панелью задач и панелью закладок, с
  небольшим запасом.
- **Один режим контента на 768–1365.** Контенту без меню остаётся 768–1023 px, с меню 799–1140.
  Диапазоны почти совпадают, поэтому вёрстка контента одна, на 1024 меняется только меню.
- **Бургер до 1024.** С боковым меню (225 px) на 768 контенту осталось бы 543 px, меньше, чем на
  767 с бургером.
- **Консоль справа с 1366.** Минимальная ширина консоли 370 px. На 1024 с меню контенту осталось
  бы 429 px.
- **Внутри режима вёрстка одинаковая,** поэтому проверяются только его края.
