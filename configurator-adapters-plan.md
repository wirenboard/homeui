# Адаптеры в конфигураторе устройств: что нужно сделать

Кому: программисту конфигуратора (пакет `wb-converter-ext` и страница
`pages/configurator` в homeui). От команды Matter, 25.11.2026. Дополнено
программистом конфигуратора по итогам обсуждения: значение по умолчанию у адаптера,
сохранение чужих ключей, порядок выпуска.

## Суть

Сейчас, чтобы в конфигураторе появился новый адаптер, нужно выпускать и пакет
конфигуратора, и веб-интерфейс: список адаптеров лежит в вашем пакете и зашит в коде
страницы. Нужно, чтобы **конфигуратор не знал заранее, кто им пользуется**: адаптер
говорит о себе сам, одним файлом своего пакета - так же, как пакеты сейчас добавляют
пункты в левое меню.

Пакет Matter свою часть уже делает. В вашем коде мы ничего не меняли.

## Два разных файла

Не путать:

| Файл | Сколько | Что внутри | Кто пишет |
|---|---|---|---|
| `/usr/share/wb-converter-ext/adapters/<id>.json` | по одному на адаптер | описание адаптера: название, пакет, служба, страница, значение по умолчанию | пакет адаптера |
| `/var/lib/wb-converter-ext/devices.yaml` | один на все адаптеры | устройства; у каждого в `adapter_settings` флажки сразу всех адаптеров | только конфигуратор |

```yaml
- did: 11
  name: Розетка в гостиной
  adapter_settings: {matter: true, alice: false}
```

## Сравнение: меню homeui и адаптеры

Образец и наш файл устроены одинаково: пакет кладёт один JSON в каталог того, кто его
читает.

### Меню homeui - как есть сейчас

| Каталог | Кто кладёт | Пример файла |
|---|---|---|
| `/usr/share/wb-mqtt-homeui/custom-menu/` | пакеты | `matter-navigation.json` (мост Matter), `configurator-navigation.json` (конфигуратор) |
| `/var/lib/wb-homeui/custom-menu/` | сам homeui, генерирует | `wb-gate-<имя>.json` |
| `/etc/wb-homeui/custom-menu/` | человек руками | любой `*.json` |

Читает бекенд homeui на каждый запрос `GET /ui/menu`, каталоги идут в этом порядке, кеша
нет; битый файл и отсутствующий каталог пропускаются. Тип файла - JSON. Файл меню моста:

```json
{
  "id": "integrations",
  "children": [
    { "id": "matter", "url": "integrations/matter", "title": { "ru": "Matter Bridge", "en": "Matter Bridge" } }
  ]
}
```

Код: `backend/wb/homeui_backend/main.py`, `CUSTOM_MENU_DIRS` и `custom_menu_handler`.

### Адаптеры конфигуратора - как должно стать

| Каталог | Кто кладёт | Файл |
|---|---|---|
| `/usr/share/wb-converter-ext/adapters/` | пакет адаптера | `<id>.json`; у Matter - `matter.json` |
| `/etc/wb-converter-ext/adapters/` | человек руками | по желанию, каталога пока нет |

Читает бекенд конфигуратора на запрос `GET /converter-ext/adapters`. Тип файла - тоже
JSON, один объект на адаптер, имя файла - идентификатор. Формат прежний плюс поле
`default`:

```json
{
  "id": "matter",
  "title": { "ru": "Matter", "en": "Matter" },
  "package": "wb-mqtt-matter-bridge",
  "service": "wb-mqtt-matter-bridge",
  "url": "integrations/matter",
  "default": true
}
```

`default` - передавать ли устройство в эту систему, если в его `adapter_settings` нет
ключа адаптера. Объявляет сам адаптер: Matter работает в локальной сети и сейчас отдаёт
устройства без ключа - `true`; Алиса отправляет устройства в облако - `false`. Нет поля -
`false`.

### Одно против другого

| | Меню homeui | Адаптеры конфигуратора |
|---|---|---|
| каталог пакетов | `/usr/share/wb-mqtt-homeui/custom-menu/` | `/usr/share/wb-converter-ext/adapters/` |
| файл пакета | `matter-navigation.json` | `matter.json` |
| запрос | `GET /ui/menu` | `GET /converter-ext/adapters` |
| что отдаёт | файлы каталога как есть | файлы каталога как есть |
| «установлен» | файл есть | файл есть |
| что знает страница заранее | ничего: `uiStore.modules` из ответа | ничего |

Отличие сегодня одно: файл `matter.json` с тем же путём пока несёт и ваш пакет.

### Где это в репозитории моста

| Файл | Куда ставится |
|---|---|
| `matter-navigation.json` | `/usr/share/wb-mqtt-homeui/custom-menu/` |
| `adapters/matter.json` | `/usr/share/wb-converter-ext/adapters/` |

Обе строки - в `debian/wb-mqtt-matter-bridge.install`.

## Что уже есть со стороны Matter

Пакет `wb-mqtt-matter-bridge` (коммит `f311fff`, ещё не отправлен) кладёт файл:

```
/usr/share/wb-converter-ext/adapters/matter.json
```

Содержимое то же, что у вашей копии. Чтобы два пакета с одним путём ставились рядом, в
нашем `debian/control` стоит `Replaces: wb-converter-ext`. Проверено на контроллере
(dpkg 1.22.22, пробные пакеты): наш файл остаётся при любом порядке установки, ваш пакет
обновляется без ошибки, после удаления Matter файла нет.

**От вас это ничего не требует и ничего не ломает** - пока вы не возьмётесь за задачи ниже.

Нужно добавить в `matter.json` моста поле `"default": true` - см. «Значение по умолчанию».

## Значение по умолчанию и чужие ключи

Решено:

1. **Нет ключа адаптера у устройства - берётся `default` из файла адаптера.** Так
   считают и страница, и сам адаптер. Сейчас мост читает «нет ключа - отдавать», а
   страница - «нет ключа - выключено»; после правки оба смотрят на `default`.
2. **При установке адаптера ключи в `devices.yaml` никто не дописывает** - ни адаптер,
   ни конфигуратор. «Нет ключа = `default`» даёт тот же результат без записи. Пишет в
   `devices.yaml` только конфигуратор и только по действию пользователя: второй писатель
   дал бы гонки, а молчаливая запись при открытии страницы меняла бы файл без спроса.
3. **Чужие ключи при сохранении остаются как были.** Конфигуратор меняет в
   `adapter_settings` только ключи адаптеров, которые показывает; остальные переносит из
   файла без изменений.

Пункт 3 - уже существующая ошибка, а не только обобщение: сейчас страница пишет
`adapter_settings: { matter }` (`stores/configurator/model.ts`, `makeDevice`) и теряет
остальные ключи. Пример: пользователь включил устройство в Алису (`alice: true`), потом
переименовал его в конфигураторе и сохранил - ключ Алисы пропал, сработал её `default:
false`, устройство молча исчезло из Алисы.

## Что нужно от вас

### Бекенд, `wb-converter-ext`

Репозиторий `wirenboard/wb-converter-mvp`, ветка `feature/INT-1287_device-configurator`.

| № | Задача | Готово, когда |
|---|---|---|
| Б1 | Новый запрос `GET /converter-ext/adapters`: отдаёт содержимое файлов `adapters/*.json` как есть, массивом, по имени файла. Ни `dpkg-query`, ни `systemctl` не зовёт | на контроллере без адаптеров отвечает `[]` и не падает, если каталога нет; битый файл пропускается с предупреждением в журнале |
| Б2 | Убрать `adapters/matter.json` из своего пакета. `alice.json` - когда свой файл начнёт класть пакет Алисы | `dpkg -S /usr/share/wb-converter-ext/adapters/matter.json` называет `wb-mqtt-matter-bridge` |
| Б3 | В `/status` оставить про адаптеры только то, что меняется в любую минуту: работает ли служба (`active` по идентификатору). `installed` убрать: файл есть - значит установлен | `/status` больше не запускает `dpkg-query` |
| Б4 | Описать поле `default` в README («Реестр адаптеров») | в таблице полей есть `default` с правилом «нет поля - `false`» |

Б2 выпускать не раньше, чем пакет Matter с файлом окажется в том же наборе пакетов: иначе
на контроллере со старым Matter адаптер пропадёт из конфигуратора. Б1, Б3 и Б4 от этого не
зависят.

Просьба к Б1: поля файла, которых бекенд не знает, отдавать как есть. Тогда адаптер сможет
позже добавить своё - например, какие типы устройств он берёт - без вашего выпуска.

### Страница, `homeui`

Ветка `feature/INT-1287_device-configurator`.

| № | Задача | Где сейчас |
|---|---|---|
| С1 | Брать список адаптеров из `GET /converter-ext/adapters` при загрузке - как `getMenu` берёт `/ui/menu`. На время перехода: если запроса нет (старый конвертер), брать `adapters` из `/status` | `stores/configurator/configurator-store.ts`, `load` |
| С2 | Убрать зашитые списки: показывать то, что пришло | `ADAPTER_IDS` и `isAdapterShown` в `pages/configurator/utils.ts`; `AdapterId = 'matter'` в `stores/configurator/types.ts`; `DEFAULT_ADAPTERS` в хранилище |
| С3 | `adapter_settings` устройства - словарь по идентификатору, а не поле `matter`. Ключи адаптеров, которых нет в списке, при сохранении остаются в файле (см. «Чужие ключи») | `stores/configurator/model.ts`, `setAdapters` в хранилище |
| С4 | Нет ключа у устройства - значение `default` адаптера; ключ пишется только когда пользователь переключил | `model.ts`, `fromConfig` |

После С2 адаптера, для которого нет файла, на странице нет вовсе: ни колонки, ни
переключателя, ни подсказки «пакет не установлен». Это решение: списка известных
адаптеров быть не должно. Заодно уходит запасной `DEFAULT_ADAPTERS`, из-за которого
страница без ответа конвертера считает Matter установленным и работающим.

Существующие тесты, которые придётся править (нужно согласие): `model.test.ts`,
`configurator-store.test.ts`, `adapter-switches.test.tsx`, `overview.test.tsx`.

## Порядок работ

1. Бекенд: Б1, Б4 - можно выпускать сразу.
2. Страница: С1-С4, с поддержкой старого `/status` на время перехода.
3. Бекенд: Б3 - не раньше страницы из п. 2. Старая страница ждёт в `/status` поле
   `installed`; без него она считает Matter не установленным и блокирует переключатель.
   Б1-Б4 сделаны одним изменением, поэтому проще выпускать конвертер и страницу в одном
   наборе пакетов.
4. Мост: `"default": true` в `matter.json`; мост читает `default` для устройств без ключа.
5. Бекенд: Б2 - когда мост с файлом в том же наборе пакетов.

## Как проверить

1. Контроллер с конфигуратором и без Matter: `/converter-ext/adapters` отдаёт `[]`, в
   обзоре нет колонки Matter, в карточке нет переключателя.
2. `apt install wb-mqtt-matter-bridge`, обновить страницу: колонка и переключатель есть;
   у устройств без ключа `matter` переключатель включён (`default: true`).
3. Остановить службу моста: пометка «служба остановлена».
4. `apt remove wb-mqtt-matter-bridge`, сохранить любое устройство: ключ
   `adapter_settings.matter` в `devices.yaml` остался.
5. Вписать руками устройству `alice: true`, переименовать его в конфигураторе и сохранить:
   `alice: true` в `devices.yaml` остался.
